Summary

BATC Remote is an independent, non-commercial companion app that lets a pilot control BeyondATC from an Android phone or tablet over the local Wi-Fi network, with everything the in-sim toolbar offers.

It uses the same WebSocket interface as the BeyondATC toolbar (protocol v3.1, port 41716). It needs no change to BeyondATC and no MSFS add-on. The official toolbar can stay open at the same time, but it is not required.

  • Status: working prototype (v0.6.0), tested on a full IFR flight (LFBZ → LFBO) with MSFS 2024, BeyondATC and an Android phone.
  • Parts: a web app for the phone (TypeScript), and a small Windows app for the PC (.NET 8, a single BatcRemote.exe that lives in the notification area) which serves the web app. The same web app also ships as an Android app (Capacitor), built from the same code.

Why a remote

The in-sim toolbar works well, but it competes with the cockpit for screen space and mouse focus. A phone or tablet next to the yoke acts like a dedicated ATC panel.

  • Home cockpits and VR: no need to open an in-sim panel or leave the VR view to answer ATC or change a frequency.
  • Full-screen flying: the whole monitor stays on the cockpit and outside view.
  • Touch-friendly: large buttons for requests, one tap to tune COM1 or COM2 from the frequency list.
  • Second screen: the ATC log, clearances (squawk, SID, altitude…) and D-ATIS stay visible without cluttering the sim.

How it works

The phone loads the web app from the PC, then talks directly to BeyondATC's WebSocket server. Nothing sits between the phone and BeyondATC.

The phone is just one more client of BeyondATC, next to the toolbar.

Component Runs on Technology Role
Web app Phone / tablet browser TypeScript, Preact, Vite The whole user interface and all protocol logic
Android app Android phone / tablet Capacitor 8 The same web app, packaged as an APK
BatcRemote.exe Simulator PC .NET 8, ASP.NET Core (Kestrel), WinForms Serves the web app over HTTP; tray icon with QR code, BeyondATC status and settings
BeyondATC Simulator PC (unchanged) WebSocket server on port 41716, as used by the toolbar

The web app finds BeyondATC on its own: by default it connects to port 41716 on the PC that served it, so the user never types an IP address. When BeyondATC runs on another PC or port, the address is resolved in this order (src/web/src/core/host.ts), the IP and the port being taken separately:

  1. ?host=IP:port in the page address (tests);
  2. the phone's own setting (Settings → Connection);
  3. the PC's setting (tray icon → Settings…), read from GET /api/config;
  4. the PC that served the page, port 41716.

The web app reads /api/config at startup, again between two reconnection attempts and when the phone comes back to the foreground, so a change made on the PC reaches the phones without reloading the page.

In the Android app, the page is packaged inside the APK instead of being served by the PC, so there is no automatic address. On first launch the user scans the QR code shown by BatcRemote.exe: the app reads the PC address from it, asks GET /api/config for BeyondATC's address and port, then connects to BeyondATC directly, as in the browser. If the PC setting is empty (BeyondATC on that PC), the PC address seen from the phone is used. A QR code holding a bare IP[:port] is taken as BeyondATC's own address, and the IP address can also be typed.

Protocol usage

BATC Remote speaks the toolbar's text protocol unchanged: frames of the form Prefix: payload (plain text or JSON) from BeyondATC, and command: argument frames back. It was worked out from the BeyondATC toolbar (v3.1) and a recorded 36-minute flight (940 messages), captured with a small sniffer page. It is not an official specification and may change with any BeyondATC update. The full message reference is in Documentation/TECHNICAL.md.

Messages handled (BeyondATC → client):

Area Prefixes
ATC log ATC, ATCTraffic, Player, Traffic, CPDLC_ATC, CPDLC_Pilot
Radios and flight Facility, Com2, RadioMute, Callsign, InfoBoxes, Progress, CPDLCCode
Actions and exchange state Actions, CommsState (+ legacy HideActions; QueuedAction is read but ignored)
Frequencies Frequencies, DATIS, DATIS_END
Co-pilot AutoTune, AutoRespond
App lifecycle LoadState, Wipe, Prompt, AppError, Settings, ToolbarVersion, Pong

Commands sent (client → BeyondATC): atc_log, frequencies, datis, settings, ping, set_action, set_frequency, set_frequency_com2, set_autotune, set_autorespond, set_setting, play_sample, start_flight, prompt_reply, ack_error, quit_to_menu, turnaround.

Behaviours the client relies on (all observed on the real flight):

  • On every new connection, BeyondATC sends a full state snapshot to all connected clients. The client applies it idempotently.
  • Several clients are supported: the toolbar and the phone received exactly the same messages.
  • Pong: goes only to the client that sent ping.
  • Frequencies is only sent on request, so the client asks for it (with datis) on connect, each time the Frequencies tab opens, and with its refresh button.
  • On connect, the client sends atc_log, settings, datis and frequencies, and repeats settings every 3 s until the settings arrive. Apart from that and the keep-alive ping, it only sends what the user triggers.

Unknown prefixes and unreadable messages are ignored and listed in the app's Settings → About section, which also warns when BeyondATC announces a protocol version other than 3.1: a protocol change is visible instead of breaking the app.

Web app

The web app is written in TypeScript (strict mode) with Preact and @preact/signals, bundled by Vite. The production build is about 83 KB of JavaScript (28 KB gzipped) and 20 KB of CSS, with no runtime dependencies beyond Preact and the Capacitor core (used only in the Android app).

It is split into three layers, so only one module ever sees the raw protocol:

Area Files Responsibility
Protocol protocol/types.ts, parser.ts, commands.ts Turns each frame into a typed message; never throws (bad JSON becomes an invalid message). Builds command strings.
Connection core/connection.ts, host.ts WebSocket lifecycle: reconnect with back-off (1, 2, 4, 8, then 15 s, plus up to 300 ms of random jitter), 8 s open timeout, ping every 15 s, restart when nothing arrives for 45 s, re-check when the phone wakes up or the network comes back. host.ts resolves the address (priority order above) and validates the IP and port typed by the user.
State core/store.ts, controller.ts, frequencies.ts One signal per area (radios, actions, log, frequencies, settings…), so a Progress update every 5 s only redraws the progress bar. The log keeps the last 400 messages. frequencies.ts groups the frequencies by airport and type. controller.ts wires the connection, parser and store, and exposes the pilot's actions to the UI.
Preferences core/prefs.ts Settings of this device only (BeyondATC address, log filters, text size, vibration, chime), saved in the browser's local storage and never sent to BeyondATC.
Notifications core/notify.ts Decides when to chime (ATC: messages to our aircraft, optionally CPDLC_ATC:; silent for 1.5 s after connecting while the log is replayed; at most one chime per 1.5 s) and synthesises the two-tone chime with the Web Audio API, so no audio file is needed.
Platform core/platform.ts, scanner.ts, screen.ts Tells whether the code runs in a browser or in the Android app, handles the QR scan of the PC (reading the code, then /api/config), and keeps the screen on and dimmed during a flight (Android app). Only these files know about Capacitor.
UI ui/*.tsx, styles.css, i18n.ts Screens, panels and dialogs; all texts in English, in i18n.ts.

Timing rules taken from the real capture:

  • Actions arrives in bursts (old list → [] → new list within 2 ms). The store keeps only the last list received within 200 ms, so buttons don't flicker.
  • During an exchange, CommsState returns to ready for about 20–30 ms between steps. Actions are disabled at once when busy, and only enabled again after 250 ms of ready.
  • When the user taps an action, it is marked as sent until BeyondATC reacts, or for 6 s at most. This prevents double sends.
  • The request mode of CommsState is treated as busy, and its text is shown as the request in progress.

Windows host (BatcRemote.exe)

BatcRemote.exe is a small .NET 8 app (C#, a single 0.8 MB file with the web app embedded) that lives in the Windows notification area. It only serves the web app's files over HTTP. It does not relay, read or change any ATC traffic.

  • Web server: ASP.NET Core minimal hosting (Kestrel) on port 8741, all network interfaces. Hashed files under /assets are cached forever; index.html is always revalidated so updates are picked up. The files are embedded in the exe (ManifestEmbeddedFileProvider), so there is no wwwroot folder to copy; --webroot <folder> serves a folder instead, for development.
  • At startup: a Windows notification shows the address to open on the phone.
  • Tray icon: the BATC Remote logo, with a green dot when BeyondATC answers on its address (this PC, port 41716 by default), orange otherwise; checked every 4 s.
  • Click: a window with a QR code of the PC's local network address (QRCoder library), to scan with the phone. When the PC has several network cards (Ethernet, Wi-Fi, VPN…), a link switches between their addresses.
  • Right-click menu: version, "unofficial tool" notice, Show QR code…, copy the address, open the app on the PC, BeyondATC status, Settings…, Launch at Windows startup (per-user HKCU\…\Run key, no admin rights), Quit.
  • Settings window: BeyondATC IP and port, with a Test button (applied at once; phones pick them up at their next connection), and the web page port (restarts the app). A button restores the defaults. Saved in %AppData%\BATC Remote\settings.json.
  • Safety: a single instance at a time (named mutex). If port 8741 is already in use, a message explains it and the settings window opens to choose another port; --port 8742 overrides the port for one launch.
  • Endpoints: GET /api/config gives phones the BeyondATC address and port chosen on the PC (with a CORS header, so the Android app can read it); GET /api/status returns the version and whether BeyondATC is reachable.

The host must keep running during a flight in the browser version, because Android can discard a background tab and the page must be reloadable. It uses a few MB of memory (workstation garbage collector). It runs on .NET 8 or any newer runtime.

Android app

The Android app wraps the same web app in a native shell with Capacitor 8, so the protocol, state and interface code are shared with the browser version. npm run build feeds both; npx cap sync android copies the build into the Android project, and Gradle produces the APK (about 6 MB).

  • Identifier: io.github.proxi64.batcremote, version 0.6.0, Android 7.0 (API 24) and newer. The only permission is Internet access.
  • Local network access: the page is served inside the app as http://localhost and unencrypted traffic is allowed, so the plain ws:// connection to BeyondATC works as in the browser.
  • Finding the PC: a small in-app plugin (QrScannerPlugin.java) uses the Google Play services code scanner. The camera screen runs in Play services: no camera permission and no image-recognition model in the APK. /api/config is then read through Capacitor's native HTTP client. The address can be scanned again or typed at any time in Settings → Connection.
  • Screen during a flight: while connected to a flight, the screen is kept on (ScreenPlugin.java). After 30 s without touch, the app drops to minimum brightness; a touch (which then only wakes the screen), an ATC call, a BeyondATC question or error brings the normal brightness back. Optionally, picking up or moving the phone does too: the accelerometer is read only while the screen is dimmed, with an adjustable sensitivity, and brief desk vibrations are ignored. No permission is needed, and the phone behaves as usual again after the flight.
  • Text size: Android's system font size is ignored (WebView text zoom fixed at 100%); only the app's own Text size setting applies.
  • Look: BATC Remote icon and splash screen, light status bar icons on the dark theme, no fullscreen button (the app is already full screen).
  • Distribution: a signed APK (BatcRemote.apk), published with BatcRemote.exe on the repository's Releases page and installed by hand. Like the browser version, the chime does not play while the phone is locked.

Features and screens

Every toolbar function is available, arranged for touch: on a phone, three tabs at the bottom (Actions, Log, Frequencies); on a tablet in landscape (900 px wide or more), the radio panel and the log on the left, Actions or Frequencies on the right.

Screen What the pilot sees and does
Top bar Connection status dot, callsign (full and short form), fullscreen button (browser only), settings
Radio panel COM1 station and frequency, COM2 (with a Monitor tag when listening only), "Muted" when a radio is off, flight progress bar, clearance boxes (taxi runway, SID, altitude, squawk…) that wrap onto several lines
Exchange banner Shown above the tabs during an exchange: Queued, Awaiting response, Transmitting, Processing…, Request in progress (with the request), or BeyondATC's own text for ATC and traffic transmissions; Sent… with the action just tapped
Actions Large buttons for every request, disabled during an exchange; above them, a co-pilot bar (headset icon, then two equal columns) with the Auto respond and Auto tune switches, which stays visible while scrolling; a turnaround card when BeyondATC offers one
Log ATC, pilot, traffic and CPDLC messages as chat bubbles, with their source and time; Traffic and CPDLC filters (remembered); a "New messages" button with a counter when scrolled up
Frequencies One tab per airport (departure first, arrival after half of the flight), types in the toolbar's order, VFR services and en-route centres below; tap = tune COM1, side button = tune COM2, with a confirmation; tuned frequencies highlighted; runways, CPDLC logon codes, ATIS letter and D-ATIS text (2 lines, tap to read it all); refresh button
Menu / loading Start a flight (IFR SimBrief; VFR SimBrief and VFR MSFS map when available), a message when the user is not logged into BeyondATC, download and loading progress
Dialogs BeyondATC questions (Yes/No), errors and warnings to acknowledge, Quit to main menu confirmation
Settings Connection (live status, address in use, one IP:port field; Auto / Manual badge in the browser, Scan button in the Android app); Display (text size in 4 steps, vibration; in the Android app, screen kept on during a flight, dimmed after 30 s, woken by a motion of the phone with a sensitivity slider); Notifications (chime, CPDLC, volume, test); all BeyondATC settings (taxi arrows, voice volume, UI sounds, co-pilot voice, voice quality with samples and premium characters left, AI traffic and densities, Navigraph live traffic); Flight (Quit to main menu); About (versions, unknown messages, disclaimer)
Notifications A short two-tone chime when ATC calls your aircraft (CPDLC optional); silent for traffic calls, your own read-backs and the history replayed on reconnect
Connection Automatic reconnection with a "Reconnecting…" banner; after 6 s, a full screen with the address, a countdown, Retry now and Change address, and from the second failed attempt a checklist (BeyondATC running, same Wi-Fi, firewall, address and port)

The interface uses a dark cockpit theme, touch targets of at least 44 px (52 px for the action buttons), short vibrations on taps (optional), and respects the system's reduce motion setting.

Quality and tooling

The protocol and state logic are tested against a real recorded flight (tests/fixtures/capture-2026-09-23.jsonl), not hand-made samples. The project has 63 automated tests (Vitest) and two development tools.

  • Parser tests (16): all 940 messages of the capture parse with no unknown or invalid result; the 15 frequencies and the real settings are read correctly; edge cases (trailing ¬, empty payloads, colons inside ATC text, | inside D-ATIS text, trailing comma in Frequencies, invalid JSON); exact format of every command.
  • State tests (9): the whole flight is replayed with its real timings and the final state is checked (station, callsign, clearances, D-ATIS, 12 ATC messages). Specific tests cover the Actions bursts, the short ready states, traffic not blocking the pilot's actions, the release of a sent action, Wipe, the D-ATIS replacement and the frequency grouping.
  • Connection tests (15): back-off delays, open timeout, ping and silent-connection restart, events from stale sockets ignored, stop, the address priority order (URL, phone, PC, page host, Android app) and the validation of the IP and port typed by the user.
  • Notification tests (5): which messages ring, the options, the quiet period after connecting and bursts; replaying the recorded flight gives exactly one chime per ATC call to our aircraft (12).
  • Screen tests (9): screen kept on during a flight, dimmed after 30 s, woken by a touch (swallowed when dimmed), an ATC call or a motion of the phone, motion sensors read only while dimmed, normal behaviour after the flight, settings switched off or changed.
  • QR scan tests (9): reading the page address shown by the PC, a bare IP[:port], rejecting unrelated QR codes, and turning the PC settings from /api/config into the BeyondATC address (including a PC that cannot be reached).
  • BeyondATC simulator (npm run sim, dev/batc-simulator.mjs): a Node.js WebSocket server on port 41716 that replays the capture and imitates BeyondATC (snapshot to every client, Pong to the sender only, a scripted exchange on set_action). Typing menu, loading, wipe, prompt, error, warning, turnaround, pause or resume in its console triggers the other screens; --menu starts on the main menu. It allows development without MSFS.
  • Sniffer (Tools/batc-sniffer.html): a single HTML page that records every frame with millisecond timestamps, counts prefixes, shows JSON structures, can open two simultaneous clients, and exports .txt / .jsonl. This is how the protocol was confirmed.

Deployment, limits and security

Setup takes about a minute: run BatcRemote.exe, scan the QR code with the phone, add the page to the home screen (or install the Android app and scan the same QR code).

Requirements: Windows with the ASP.NET Core 8 and Windows Desktop 8 runtimes (or newer), BeyondATC running, phone and PC on the same Wi-Fi, and Windows Firewall allowing port 8741 (the app) and 41716 (BeyondATC) on private networks. Tested with Firefox and Samsung Internet on Android, and with the Android app (which needs Google Play services for the QR scan; the IP address can also be typed).

Limits of plain HTTP on a LAN: browsers reserve some features for secure (HTTPS) pages.

  • The browser version cannot keep the screen awake (Screen Wake Lock API); the user sets a longer screen timeout instead, or uses the Android app, which does it.
  • The home-screen shortcut opens in a browser tab rather than as an installed standalone app; an in-app fullscreen button hides the browser bars.
  • Sound only plays after a first tap in the app, and not while the screen is locked or the browser is in the background.
  • The page must be reloadable from the PC, so BatcRemote.exe stays running during the flight.

An HTTPS page could not work this way anyway: a secure page is not allowed to open a plain ws:// connection to a local network address.

Security: port 41716 accepts connections from any device on the local network, with no authentication. Anyone on the same Wi-Fi who knows the protocol could send commands to BeyondATC (for example quit_to_menu). This already applies to BeyondATC today; BATC Remote does not open anything new. On a home network the risk is low; avoid using it on public or shared networks.

Protocol observations

The interface works very well for a second client. A few behaviours observed on the recorded flight matter for anyone writing a client:

  1. QueuedAction and the queued text lag by one action. Tapping "Request Taxi to Runway" produced QueuedAction: Request IFR Clearance (the previous one); tapping "Affirm" produced queued: "FL120". BATC Remote ignores this text and shows the request text instead.
  2. Actions is sent three times per update (old list, [], new list, within 2 ms). Clients therefore need a short debounce.
  3. CommsState briefly returns to ready (20–30 ms) between the steps of one exchange, so clients need a delay before enabling the actions again.
  4. Actions lists end with a trailing ¬ ([A¬B¬]), which creates an empty last item.
  5. The snapshot is re-sent to every client whenever any client connects. That is harmless, but clients must apply it idempotently.
  6. Actions sent by one client are not echoed to the others: only their effects are visible (CommsState, then Player:, then ATC:).

Code and build

The code is small and organised by responsibility. The full source code is in this repository.

src/web/                   Web app (TypeScript + Preact + Vite)
  src/main.tsx             Entry point
  src/protocol/            BeyondATC protocol: types, parser, commands
  src/core/                Connection (connection.ts), address resolution (host.ts),
                           state (store.ts, controller.ts), preferences (prefs.ts),
                           frequency grouping (frequencies.ts), notifications (notify.ts),
                           platform detection (platform.ts), QR scan (scanner.ts),

Build: Node.js 22+ and the .NET 8 SDK. build.ps1 installs the web dependencies, runs type checking and tests, builds the web app into the host's wwwroot, then publishes a single BatcRemote.exe for Windows x64 into dist\, with the web app embedded. When the Android SDK is installed (Android Studio), it also builds the Android app: the signed dist\BatcRemote.apk when src/web/android/keystore.properties points to a signing key (see keystore.properties.example; the key and its passwords are never committed), otherwise dist\BatcRemote-debug.apk, for testing only.
